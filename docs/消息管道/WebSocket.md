## WebSocket 的设计思想

WebSocket 的核心设计思想是：**在单个 TCP 连接上建立全双工、持久化的通信通道，让客户端和服务端可以随时主动向对方发送消息**，彻底改变 HTTP“请求-响应”的半双工模式。

传统 HTTP 中，每次通信都由客户端发起请求，服务端被动响应；如果服务端有状态变化想主动通知客户端，只能依赖轮询或长轮询（Long Polling），效率低、延迟高、资源浪费。WebSocket 通过一次握手（HTTP Upgrade 协议切换）升级为 WebSocket 协议，此后双方地位对等，可以在任意时刻发送数据帧，实现真正的双向实时通信。

**设计要点：**

- **一次握手，持久连接**：基于 HTTP 的 `Upgrade` 头，将连接从 HTTP 协议升级为 WebSocket 协议，连接保持开放直到主动关闭。
- **全双工**：双方可同时独立收发数据，没有“请求-响应”的强制性配对。
- **低开销**：消息帧头部仅 2~10 字节（HTTP 请求头通常几百字节），且没有重复的握手开销。
- **基于事件驱动**：通过 `onopen`、`onmessage`、`onerror`、`onclose` 等事件来处理通信。
- **支持文本与二进制**：可以发送 UTF-8 文本或原始二进制数据（如音频、视频、游戏状态）。

## 举例说明

### 例1：在线聊天室（即时通讯）

- **传统 HTTP 方式**：客户端每隔 2 秒轮询服务器“有没有新消息”，产生大量无效请求；消息延迟至少 2 秒；服务器需承受高并发轮询压力。
- **WebSocket 方式**：用户登录后建立 WebSocket 连接。用户 A 发送一条消息，服务器立即推送给所有在线用户（包括用户 B）。消息延迟是毫秒级，且没有额外轮询请求。

**效果**：实时、高效、省资源，用户感知到“消息秒到”。

### 例2：多人实时协作（如 Google Docs 协作编辑）

- **场景**：多个用户同时编辑同一个文档，需要看到其他人的光标位置、实时看到文字插入/删除。
- **WebSocket 作用**：每个用户的编辑操作（如插入字符、删除段落）通过 WebSocket 发送给服务器，服务器广播给其他协作成员。由于 WebSocket 是全双工的，服务器也能主动推送“另一个用户正在输入”的状态。

**效果**：低延迟同步，实现“所见即他人所得”的协同体验。

### 例3：实时金融行情（股票/加密货币报价）

- **场景**：股票价格每秒变化数次，客户端需要实时显示最新价格、买卖盘深度。
- **传统 HTTP**：即使每秒轮询一次，仍有 1 秒延迟，且高频轮询对服务器压力巨大。长轮询虽减少空请求，但每次重新建立连接仍有延迟和开销。
- **WebSocket**：服务端一收到交易所的新价格（比如通过 WebSocket 本身连接到交易所），立刻推送给所有客户端。客户端可以实时刷新 K 线图和盘口数据。

**效果**：延迟低于 10 毫秒，支撑高频交易监控系统。

### 例4：实时游戏（多人对战/棋牌）

- **场景**：玩家移动、发射子弹、碰撞检测等需要在几十毫秒内同步给其他玩家。
- **WebSocket**：客户端上传玩家操作，服务器广播状态更新。全双工特性允许服务器主动下发“游戏开始倒计时”、“敌方位置”等消息，无需客户端请求。

**效果**：流畅的实时对战体验，避免因网络延迟造成的卡顿和不同步。

## 适用场景

| 场景类别         | 具体示例                                    | 为什么适合 WebSocket                     |
| ---------------- | ------------------------------------------- | ---------------------------------------- |
| **即时通讯**     | 聊天、私信、群聊通知                        | 双向低延迟推送，无需轮询                 |
| **实时协作**     | 文档协同、白板、代码结对                    | 需要同步光标、编辑操作、版本状态         |
| **实时数据推送** | 股票/加密货币行情、体育比分、IoT 传感器数据 | 高频小数据更新，要求低延迟               |
| **在线游戏**     | 多人射击、MOBA、棋牌                        | 低延迟双向消息交换，支持二进制协议       |
| **实时监控**     | 服务器仪表盘、日志流、任务进度              | 服务器主动推送状态变化，前端实时更新图表 |
| **直播互动**     | 弹幕、礼物、投票                            | 观众与主播之间双向消息，延迟容忍度低     |
| **远程控制**     | 远程桌面、SSH 终端、设备控制                | 双向传输键盘输入和屏幕更新（二进制）     |

## WebSocket vs Webhook vs WebStream

| 特性                 | WebSocket                | Webhook                                   | Web Streams                                 |
| -------------------- | ------------------------ | ----------------------------------------- | ------------------------------------------- |
| **通信模式**         | 双向实时，持久连接       | 单向（服务端 → 客户端回调），异步 HTTP    | 单向/可转换流（通常是服务端 → 客户端）      |
| **连接性质**         | 长连接（TCP）            | 短连接（每个事件一次 HTTP 请求）          | HTTP/2 或基于流的长连接（如 SSE、fetch 流） |
| **延迟**             | 极低（毫秒级）           | 取决于网络和重试，通常秒级                | 低（流式传输首字节时间短）                  |
| **适用场景**         | 双向交互、高频实时更新   | 事件通知、系统集成（如支付回调、CI 触发） | 大文件分块、AI 流式生成、实时仪表盘（单向） |
| **协议开销**         | 小（帧头 2-10 字节）     | 大（每个请求 HTTP 头 + body）             | 中等（基于 HTTP/2 或 chunked encoding）     |
| **是否需要公网 URL** | 不需要（客户端主动连接） | 需要（服务端需能回调客户端）              | 不需要（客户端发起请求）                    |

**总结**：

- 如果你需要 **服务器主动推数据给客户端**，且客户端无需频繁向服务器发送数据，可以用 **Server-Sent Events (SSE)** 或 **WebStream**（更通用）。
- 如果你需要 **双向实时通信**（如聊天、游戏、协作），WebSocket 是最合适的选择。
- 如果你需要 **跨服务、异步的事件通知**（如支付成功触发发货），Webhook 更简单轻量。

WebSocket 填补了 Web 应用中“实时双向通信”的空白，是构建现代实时交互系统的基石技术之一。
