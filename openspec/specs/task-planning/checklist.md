# 任务规划检查清单

> 在制定任务列表时，检查是否遵循了最佳实践

---

## ✅ 开始规划前

### 调研阶段

- [ ] 是否调研了现有 SDK/库的能力？
  - 检查 npm 包是否存在
  - 阅读 SDK 文档
  - 查看示例代码

- [ ] 是否检查了项目已有的基础设施？
  - 查看 INFRASTRUCTURE.md
  - 搜索相关代码文件
  - 检查已有的封装

- [ ] 是否区分了"实现"和"集成"？
  - "实现": 从零开发功能
  - "集成": 封装 SDK 或复用基础设施

- [ ] 是否评估了真实代码量？
  - 预估代码行数
  - 参考类似实现
  - 考虑复用节省

---

## 📋 拆分任务时

### 粒度检查

- [ ] 每个任务是否是一个完整的工作单元？
  - ✅ "配置 Amazon API 集成" (完整)
  - ❌ "安装依赖" (单一步骤)
  - ❌ "创建配置文件" (单一步骤)

- [ ] 任务粒度是否合理？
  - ✅ 0.5-2 小时可完成
  - ❌ < 30 分钟 (过细)
  - ❌ > 4 小时 (过粗)

- [ ] 是否避免了单一步骤拆分？
  - ❌ "安装依赖 X"
  - ❌ "创建配置文件"
  - ❌ "添加环境变量"
  - ✅ "配置和依赖管理" (合并以上)

### 避免重复

- [ ] 是否避免了测试单独列出？
  - ✅ "实现 API 客户端（含测试）"
  - ❌ "实现 API 客户端" + "创建单元测试" + "创建集成测试"

- [ ] 是否避免了重复已有功能？
  - 检查 SDK 是否已提供
  - 检查基础设施是否已实现
  - 检查项目中是否已有类似实现

- [ ] 是否区分了核心任务和辅助任务？
  - 核心任务: 实现业务逻辑
  - 辅助任务: 配置、文档、部署

---

## ⏱️ 评估工作量时

### 代码量 vs 任务数

- [ ] 是否对比了代码量 vs 任务数量？

  **合理性参考**:

  ```
  简单集成:  100-200 行 → 1-2 任务
  中等实现:  300-500 行 → 2-4 任务
  复杂系统:  500-1000 行 → 4-8 任务
  ```

- [ ] 任务数量是否与代码量匹配？
  - ⚠️ 任务数量 >> 代码量 → 可能过度拆分
  - ⚠️ 任务数量 << 代码量 → 可能粒度过粗

### 时间预估

- [ ] 是否考虑了 SDK 提供的功能？
  - SDK 提供功能 → 估算时间减少 50-80%
  - 自己实现 → 按正常估算

- [ ] 是否考虑了基础设施复用？
  - 可复用 → 估算时间减少 30-50%
  - 自己实现 → 按正常估算

- [ ] 预估时间是否合理？
  - 对照历史数据
  - 考虑学习曲线
  - 预留缓冲时间

## ⚠️ 危险信号

### 立即停止并重新审视

如果出现以下情况，任务拆分可能有问题：

#### 1. 任务数量异常

```
⚠️ 任务数量 >> 代码量

例如:
- 预估代码: 200 行
- 任务数量: 40 个
- 平均每任务: 5 行

→ 这明显过度拆分了！
```

#### 2. SDK 提供的功能

```
⚠️ 任务是 SDK 已提供的功能

例如:
- "实现 LWA 认证" → amazon-sp-api SDK 已提供
- "实现 AWS 签名" → amazon-sp-api SDK 已提供
- "实现令牌刷新" → amazon-sp-api SDK 已提供

→ 应该改为 "配置和封装 SDK"
```

#### 3. 基础设施重复

```
⚠️ 任务是已实现基础设施的重复

例如:
- "实现事务管理" → TransactionManager 已实现
- "实现错误重试" → TransactionManager 已实现
- "实现健康检查" → PoolHealthCheck 已实现

→ 应该改为 "复用基础设施 X"
```

#### 4. 测试单独列出

```
⚠️ 测试单独列出

例如:
- [ ] 实现功能 A
- [ ] 创建单元测试 A
- [ ] 创建集成测试 A
- [ ] 性能测试 A

→ 应该合并为 "实现功能 A（含测试）"
```

## 🎯 修正指南

### 如何合并过度拆分的任务

**Before**:

```markdown
- [ ] 2.1.1 安装依赖 A
- [ ] 2.1.2 安装依赖 B
- [ ] 2.1.3 创建配置 schema
- [ ] 2.1.4 更新配置文件
- [ ] 2.1.5 创建 .env.example
- [ ] 2.1.6 验证配置加载
```

**After**:

```markdown
- [ ] 2.1 配置和依赖管理
      (包含：安装依赖、配置文件、环境变量、验证)
      预估: 1 小时
      代码量: ~50 行（配置文件）
```

### 如何利用 SDK 能力

**Before**:

```markdown
- [ ] 实现 LWA 认证
- [ ] 实现 AWS 签名
- [ ] 实现令牌刷新
- [ ] 实现速率限制
```

**After**:

```markdown
- [ ] 封装 amazon-sp-api SDK
      (SDK 已提供：认证、签名、刷新、速率限制)
      预估: 2 小时
      代码量: ~100 行（封装层）

      参考: TaobaoApiClient 模式
```

### 如何复用基础设施

**Before**:

```markdown
- [ ] 实现事务管理
- [ ] 实现错误重试
- [ ] 实现健康检查
```

**After**:

```markdown
- [ ] 集成 TransactionManager
      (复用已有的事务管理和错误处理)
      预估: 30 分钟
      代码量: ~20 行（配置）

      参考: INFRASTRUCTURE.md - TransactionManager
```

## 📝 示例：修正一个任务列表

### 原始版本 (40 tasks)

```markdown
## 2.1 依赖和配置 (6 tasks)

- [ ] 2.1.1 安装 amazon-sp-api 依赖
- [ ] 2.1.2 安装 aws-sdk-client-v3 依赖
- [ ] 2.1.3 创建 Amazon 配置 schema
- [ ] 2.1.4 更新配置文件
- [ ] 2.1.5 创建 .env.example
- [ ] 2.1.6 验证配置加载

## 2.2 SP-API 客户端 (10 tasks)

- [ ] 2.2.3 创建 auth/LWAAuth.ts
- [ ] 2.2.4 创建 auth/AWSSigner.ts
- [ ] 2.2.5 创建 AmazonSPApiClient.ts
- [ ] 2.2.6 实现令牌刷新
- [ ] 2.2.7 添加错误处理和重试
- [ ] 2.2.8 实现速率限制处理
- [ ] 2.2.9 创建单元测试
- [ ] 2.2.10 测试认证流程
      ...
```

**问题**:

1. ❌ 过度拆分 (6 个配置任务)
2. ❌ SDK 已提供 (LWAAuth, AWSSigner, 令牌刷新, 速率限制)
3. ❌ 测试单独列出
4. ❌ 忽视基础设施 (错误重试)

### 修正版本 (5 tasks)

```markdown
## Phase 2: Amazon API 实现

### 2.1 配置和依赖 (1 task)

- [ ] 2.1 安装 amazon-sp-api 并配置 Amazon 集成
      (包含：安装依赖、配置 plugin.json、环境变量、验证)
      预估: 1 小时
      代码量: ~50 行

### 2.2 API 客户端封装 (2 tasks)

- [ ] 2.2.1 创建 AmazonSPApiClient 封装 SDK
      (SDK 已提供：认证、签名、刷新、速率限制)
      参考: TaobaoApiClient 模式

      预估: 2 小时
      代码量: ~100 行

- [ ] 2.2.2 创建 AmazonProductApi 封装产品 API
      (ProductPricing + CatalogItems, 数据转换)
      预估: 2 小时
      代码量: ~100 行

### 2.3 Adapter 集成 (1 task)

- [ ] 2.3 重构 AmazonAdapter 使用真实 API
      (替换 Mock, 数据合并, 降级逻辑)
      参考: TaobaoAdapter 模式, 复用 TransactionManager
      预估: 2 小时
      代码量: ~150 行

### 2.4 测试和文档 (1 task)

- [ ] 2.4 添加测试和更新文档
      预估: 2 小时
      代码量: ~200 行
```

**改进**:

1. ✅ 合并过度拆分的任务
2. ✅ 利用 SDK 能力，避免重复实现
3. ✅ 测试与实现合并
4. ✅ 明确代码量和时间预估
5. ✅ 参考现有模式和基础设施
