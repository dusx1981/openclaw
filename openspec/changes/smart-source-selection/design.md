## Context

当前 `BasePlatformAdapter.fetchWithFailover()` 使用硬编码优先级顺序：

```
官方 API → 第三方 API → 爬虫
```

问题：
- 无法动态调整策略（如成本敏感场景优先用免费源）
- 无法根据历史成功率自动避让故障源
- 返回结果只标记 `fallback_source`，无法区分具体类型

## Goals / Non-Goals

**Goals:**
- 策略模式实现数据源选择，支持多种选择策略
- 自动追踪数据源健康度，故障时智能避让
- 返回结果标记具体 `sourceType`

**Non-Goals:**
- 不做机器学习预测
- 不做实时竞价选择
- 不改变现有降级层级结构

## Decisions

### Decision 1: 策略模式设计

**选择**: 使用策略接口 + 配置驱动

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                      SourceSelectionStrategy 策略接口                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   interface SourceSelectionStrategy {                                       │
│     select(sources: DataSource[], context: SelectionContext): DataSource   │
│   }                                                                         │
│                                                                             │
│   实现类：                                                                   │
│   ├── PriorityStrategy        按优先级选择（默认）                          │
│   ├── CostFirstStrategy       成本优先，选择最便宜的可用源                  │
│   └── ReliabilityStrategy     可靠性优先，选择成功率最高的源                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**理由**:
- 策略模式符合开闭原则，新增策略无需改 Adapter
- 配置驱动，运行时可切换
- 简单直观，易于理解

**备选方案**:
- 策略工厂 + 规则引擎 → 过于复杂
- 硬编码 if-else → 不灵活

### Decision 2: 健康度追踪设计

**选择**: 轻量级滑动窗口统计

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                      SourceHealth 健康度追踪                                │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   interface SourceHealth {                                                  │
│     sourceId: string                                                        │
│     recentAttempts: number        // 最近 N 次尝试                         │
│     recentSuccesses: number       // 最近 N 次成功                         │
│     lastError?: string            // 最后错误信息                          │
│     lastSuccessAt?: Date          // 最后成功时间                          │
│   }                                                                          │
│                                                                             │
│   计算公式:                                                                  │
│   healthScore = recentSuccesses / recentAttempts                           │
│                                                                             │
│   选择时: healthScore < 0.5 的源降权或跳过                                  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**理由**:
- 滑动窗口比全量统计更能反映当前状态
- 计算简单，性能开销小
- 内存存储，无需持久化

**备选方案**:
- 持久化到 Redis → 增加依赖，过度设计
- 全量历史统计 → 无法反映近期变化

### Decision 3: 返回结果增强

**选择**: 增加 `sourceType` 字段

```typescript
interface FetchResult<T> {
  // ... 现有字段
  sourceType?: "official_api" | "third_party_api" | "crawler"
}
```

**理由**:
- 调用方可根据来源类型做不同处理
- 监控统计更精确
- 向后兼容（可选字段）

### Decision 4: 选择流程

**选择**: 单次选择 + 故障时重试下一个

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                      数据源选择流程                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   1. 获取所有可用数据源                                                     │
│   2. 过滤掉 healthScore < 0.3 的源（严重故障）                              │
│   3. 使用策略选择最佳源                                                     │
│   4. 执行请求                                                               │
│      ├─ 成功 → 更新健康度，返回结果                                        │
│      └─ 失败 → 记录失败，回到步骤 3 选择下一个源                            │
│   5. 所有源都失败 → 抛出异常                                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**理由**:
- 一次选一个，失败再换，避免浪费
- 健康度过滤提前排除严重故障源
- 保持简单，符合"稳定、准确"目标

## Risks / Trade-offs

**Risk 1**: 健康度统计不准确导致误判
→ Mitigation: 滑动窗口 N=20，足够样本量

**Risk 2**: 策略选择开销
→ Mitigation: 策略计算是 O(n) 遍历，数据源数量少（≤3），可忽略

**Trade-off**: 不做持久化，重启后健康度重置
→ 可接受：健康度本身就是近期表现，重启后重新统计是合理的
