## Context

当前淘宝数据采集系统包含三层数据源：官方 API (优先级1)、第三方 API (优先级2)、爬虫 (优先级3)。系统已实现熔断器、降级管理、错误分类等可靠性机制。

缺少快速验证工具来：
- 测试真实采集成功率
- 验证降级路径是否正确触发
- 采集样本数据并评估质量
- 生成可读的验证报告

## Goals / Non-Goals

**Goals:**
- 提供命令行工具 `openclaw meichao validate taobao` 快速验证采集效果
- 支持指定采集数量、超时参数
- 自动记录成功率、降级次数、数据源使用分布
- 支持模拟故障场景验证降级流程
- 生成包含数据样本和统计信息的报告
- 支持输出为 JSON 或可读文本格式

**Non-Goals:**
- 不实现生产环境监控（这是独立功能）
- 不修改现有 TaobaoAdapter 的核心采集逻辑
- 不支持其他平台（本迭代聚焦淘宝）
- 不实现定时验证任务

## Decisions

### Decision 1: 验证命令实现方式

**选择**: 独立命令模块 `src/commands/validate.ts`

**理由**: 
- 与现有采集逻辑解耦，不影响生产代码
- 便于添加验证专用逻辑（采样、统计、报告）
- 可复用现有 TaobaoAdapter 和降级机制

**备选方案**:
- 在 TaobaoAdapter 添加验证模式 ❌ 污染生产代码
- 独立脚本 ❌ 无法复用项目基础设施

### Decision 2: 报告格式

**选择**: 支持两种格式 - 默认文本报告 + JSON 格式（--json 参数）

**理由**:
- 文本报告便于开发者快速查看
- JSON 格式便于集成 CI/CD 和自动化处理

### Decision 3: 故障模拟方式

**选择**: 使用现有 Chaos 工具模拟故障

**理由**:
- 已有完善的 Chaos 测试工具
- 支持注入延迟、失败、网络错误等
- 可复用测试框架基础设施

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 验证过程可能消耗 API 配额 | 添加 --dry-run 模式和采集数量限制 |
| 网络不稳定影响验证结果 | 报告中包含重试次数和网络状态 |
| 样本数据可能敏感 | 支持脱敏输出（--mask-sensitive）|
